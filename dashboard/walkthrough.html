Salesforce to finance integration

Overview Mappings Walkthrough

A ten-minute walkthrough

Seven stops that show the whole project on this dashboard. Each one says where to click, what to point out and what you should see.

What it isSalesforce and a legacy finance system kept in step by MuleSoft.
Three flowsCustomers to finance, invoices to Salesforce, a nightly payments file.
Four Mule appsThree system APIs and one process API, on one local runtime.
Before you startEvery card on the Overview should have a green dot.

  1. The picture

    1 minute · Overview

    Do
    Point at the three zones left to right: Salesforce, MuleSoft, on-premises finance.
    Say
    Salesforce and finance never talk to each other. Each system API wraps one system; the process API in the middle holds the rules. Replace the finance system and only one box changes.
    See
    Animated lines where both ends are up, and matching counts on the Invoices and Oracle cards.

  2. A change in Salesforce reaches finance

    2 minutes · Salesforce, then Overview

    Do
    Click the Accounts card and open Accounts in Salesforce. Edit any Account, for example its phone number, and save. Come back here.
    Say
    Nothing polls. Salesforce publishes a change event, the Salesforce API is subscribed to it, and the process API upserts the customer in finance. The upsert is keyed on the Salesforce ID, so the same event twice changes nothing.
    See
    Within a few seconds, a new Account change event entry at the top of Run history, with the result UPDATED.

  3. Invoices flow the other way

    1 minute · Overview

    Do
    Click Sync invoices, then click it again.
    Say
    The sync reads only invoices changed since a watermark, and moves the watermark only after Salesforce accepts the batch. A failed run re-reads the same rows, and the upsert makes that harmless. It also runs by itself every five minutes.
    See
    Two Invoice sync entries reading 0 invoices, because nothing has changed. Full resync sends all 15 again and creates none.

  4. A legacy file with bad rows

    2 minutes · Overview

    Do
    Choose payments_20261117_bad.csv in the dropdown and click Drop payments file. Wait about 15 seconds, then click the SFTP server card.
    Say
    The file lands on the SFTP server as the old finance system would deliver it. Each row is validated and applied on its own, so one bad row never fails the file. Rejected rows go to a rejects file with a reason.
    See
    A Payments file entry in Run history, the file under Archive, and a rejects file listed. On a fresh database: 2 applied, 6 rejected, and the status counts move on both invoice cards. If the file was processed before: every valid row shows as a duplicate, which is the point to make about safe re-runs.

  5. The mappings, live

    2 minutes · Mappings

    Do
    Open Payments CSV to finance payments. In the input, change a date to 31/02/2026 and press Ctrl+Enter. Then open Salesforce Account to finance customer and change the state to victoria.
    Say
    This is the real DataWeave file running on the Mule engine, not a copy. The lookup tables that translate one system's vocabulary into the other's live in one shared module.
    See
    The row turns invalid with a reason. The state becomes VIC.

  6. Proving both sides agree

    1 minute · Overview

    Do
    Click Reconcile.
    Say
    Each side hashes the synced fields of every customer: Oracle in PL/SQL, Mule in DataWeave. Equal hashes mean the records agree, without comparing them field by field. This is the evidence you want after a migration or before a cutover.
    See
    A Reconciliation entry with inSync true and 8 matched.

  7. When something breaks

    1 minute · Overview

    Do
    Click finance-sys-api, then its stop icon. Wait a few seconds, click Reconcile, then press the play icon to start the app again.
    Say
    The process API retries a failing system API three times, then gives up with a clear error. It does not retry bad data, which would never succeed. Every log line carries a correlation ID, so one ID traces a record across all four apps.
    See
    The card turns red and its connections stop moving. The failed run appears with a correlation ID. Click the line between the process API and the finance API to see the error on that connection.

Questions you are likely to get

  • Why four apps for three flows? To show the pattern at a size that can be explained. A real two-system integration this small would not need all of it.
  • What stops a payment being applied twice? A unique payment reference in finance. The stored procedure reports a repeat as a duplicate instead of failing.
  • What if a file arrives while the process API is down? It stays in the inbound folder and is tried again on the next poll.
  • How does Mule log in to Salesforce? It signs a token with a private key, and Salesforce checks it against a certificate on the External Client App. No password is stored.

What is not built

  • MUnit tests are written for one app only and have not been run.
  • No CI/CD pipeline, and nothing is deployed to CloudHub.
  • No TLS on the local listeners, no API Manager policies, no alerts.
  • No operational runbook.

Starting and resetting

To start everything on another day, run this from the project folder, then press the play icon in the green MuleSoft zone:

.\scripts\start-dashboard.ps1

To put the finance data back to its starting state, rebuild the database, then click Migrate customers and Full resync here so Salesforce matches it again:

cd infra
docker compose down -v
docker compose up -d

The reset removes every payment applied during a demo. The Salesforce Accounts stay; the migration links them to the rebuilt customers by their finance customer code.
